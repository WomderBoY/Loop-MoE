# Looped MoE 的 CPU–GPU 专家调度：文献调研与初步实验

调研日期：2026-11-11。本文是文献核查与实验建议，尚未运行模型、复现实验或测得加速。论文公开代码的存在已核查，代码可运行性与论文结果未复现。

## 1. 判断

这个方向在技术上可行，但“专家跨迭代重复，因此缓存专家，并用 CPU 补偿未命中”已经有非常接近的先行工作，尤其是 OLED-MoE。值得验证的问题是：**深度循环的阶段、物理参数共享、复用距离及剩余循环次数，是否能让调度显著优于直接迁移现有方法。**

在此次 arXiv/alphaXiv、论文正文及作者公开仓库检索范围内，没有找到明确以深度循环 Looped MoE 为对象、联合设计 CPU–GPU 专家缓存与异构执行、并完成端到端评估的直接对应工作。这是有限范围内的检索结论，不能证明不存在，也不宜直接宣称“首个”。

检索覆盖：LoopMoE / looped MoE / recurrent-depth transformers 与 expert offloading、scheduling、cache、prefetching、CPU–GPU 的交叉；补查 OLED-MoE、HybriMoE、MoE-CORE、Foil、LatentLoop、Loopie 及相关服务调度。

## 2. 相关工作与边界

| 工作 | 已研究的内容 | 对本方向的意义 |
|---|---|---|
| [LoopMoE](https://arxiv.org/html/2606.04438v2) | 循环 MoE 架构、IterAdaLN、容量平衡、跨循环路由分析；报告常规推理时延，未提出 CPU–GPU 专家调度器 | 提供动机，但不能据此推定所有循环、模型和任务均有强复用 |
| [OLED-MoE](https://arxiv.org/html/2609.33385v1) | dLLM 相邻去噪迭代间专家保留、按层缓存容量分配、同时考虑当前负载与未来复用的 CPU/GPU 补偿 | 最接近、必须比较的先行工作；不是深度循环模型，但核心思路非常接近 |
| [HybriMoE](https://arxiv.org/abs/2504.05897) | 层内 CPU/GPU 动态任务分配、收益驱动的跨层预取、路由分数缓存 | 可作为调度执行框架与强基线；它已利用分数预测未来复用 |
| [Fiddler](https://arxiv.org/abs/2402.07033) | 用 CPU 计算未驻留专家，以传输激活替代传输大专家权重 | 解释小 batch 下 CPU 路径为何值得保留；可作为较简单异构执行基线 |
| [MoE-Infinity](https://arxiv.org/abs/2401.14361) | 请求级激活轨迹、专家缓存和预取 | “根据历史路由预测专家”本身不是新贡献 |
| [ProMoE](https://arxiv.org/abs/2410.22134) | 利用中间结果预测后续专家，提前加载 | 预取及隐藏传输本身也不是新贡献 |
| [MoE-CORE](https://arxiv.org/abs/2610.01950) | prefill/decode 分别设计传输路径，结合非均匀层缓存、路由历史替换和跨层预取 | 层间容量分配和历史复用管理已有丰富先例；主配置与可选近似配置应分开比较 |
| [Foil](https://arxiv.org/abs/2609.35751)、[LatentLoop](https://arxiv.org/abs/2610.19975) | 分别探索专家池/循环形状与注意力解绑、不同 visit 的非对称计算分配 | 架构研究，不应将其“compute allocation”误认为 CPU/GPU 专家放置 |
| [Loopie](https://arxiv.org/html/2607.16051v3) | 逐层循环的 MoE；论文讨论短参数复用距离对基础设施的好处 | 系统局部性已有明确讨论，但未看到本问题所需的专家异构调度算法 |
| [Continuous Depth Batching](https://arxiv.org/abs/2608.09444) | 为不同循环深度的 token 安排批处理和边界阶段 | 说明 loop-aware serving 已有工作；调度对象不是 CPU/GPU 专家 |

OLED-MoE 的公开实现：[flashserve/OLED-MoE](https://github.com/flashserve/OLED-MoE)。HybriMoE 的公开实现：[PKU-SEC-Lab/HybriMoE](https://github.com/PKU-SEC-Lab/HybriMoE)。它们目前的公开说明分别围绕 dInfer/dLLM 和既有 AR MoE 模型；不能假设直接加载任意循环模型即可复现。

### 2.1 LoopMoE 的动机需要保留阶段差异

LoopMoE §6.2、附录 A.7 的结论是：进入循环、循环内部、退出循环具有不同路由行为。中间两轮形成最稳定的专家组合；最后一轮的隐藏状态仍接近上一轮，但专家集合出现明显变化，第二个循环层尤其突出。该分析使用 BBH，不能自动推广到自由生成、其他领域和其他架构。[原文](https://arxiv.org/html/2606.04438v2)

因此要同时测量离散专家选择和连续 hidden-state 相似度，不能只用 cosine similarity 推断预取命中。也不要把“相对较高的 Jaccard”直接写成系统缓存命中率。

### 2.2 OLED-MoE 已占据的核心思路

OLED-MoE 用当前 gate 分数和 dLLM 本来就有的 token confidence 估计下一次同层访问的专家价值。它保留高价值专家、按层调整缓存，并在缺失时联合考虑当前 token 负载和未来复用，决定 CPU 执行或 H2D 加载。重点是跨迭代保留，不是额外增加一轮预测性预取。[原文 §4](https://arxiv.org/html/2609.33385v1)

所以“让高复用专家留 GPU，低复用专家放 CPU”以及“把未来复用加入成本模型”，都不足以单独构成本方向的新贡献。潜在增量应落在深度循环特有信号是否必要、是否有效，以及相应执行约束。

### 2.3 HybriMoE 已提供的组件

HybriMoE 的调度优先考虑 GPU 上已缓存且负载高的专家、CPU 上未缓存且负载低的专家，以及应向 GPU 传输的高负载专家；通过模拟 CPU/GPU/PCIe 时间线安排任务。它还根据预取对完成时间的影响选择预取对象，并对较高路由分数做历史平滑用于缓存替换。[原文 §IV](https://arxiv.org/abs/2504.05897)

不能把 HybriMoE 简化成“完全不预测复用的传统方法”。公平实验必须保留其缓存与预取能力。

## 3. 可行性：复用怎样转成时延收益

以下为基于文献的系统分析与待验证推论，不是论文已证明的结论。

### 3.1 同一物理权重在一个 token 内重复使用

普通 Transformer 不同层的同号专家通常不是同一份权重。循环 MoE 中，同一物理层在不同 loop 访问相同专家时，可真正复用同一份 GPU 权重副本。专家缓存应以“物理专家池、专家 ID、权重版本/精度”为身份，不应把 loop index 当作需要复制权重的新层编号。

权重共享不意味着输出可复用：下一轮 hidden state 已改变，仍需重新执行专家。保持精确路由的调度优化可以避免重训；CPU/GPU 浮点内核差异仍应单独验证。

推理中 CPU 若始终保存不可变权重，GPU 淘汰通常只需释放副本，无需把专家权重写回 CPU。主要传输是 H2D 权重；CPU 计算路径则需要激活的 D2H 和结果的 H2D。

### 3.2 不能只看当前一次调用

设专家传输成本为 H，预计驻留期间使用 M 次，每次 CPU/GPU 计算成本分别为 C、G。忽略并发和其他开销时，搬到 GPU 的粗略条件为：

\[
H+MG<MC\quad\Longleftrightarrow\quad M(C-G)>H.
\]

举例：H=1.2 ms、C=0.5 ms、G=0.1 ms，一次使用时 CPU 更快，四次使用且中途不被淘汰时 GPU 路径总成本 1.6 ms，低于 CPU 的 2.0 ms。这些数值仅是说明，不是实测。

真实模型必须加上激活传输、量化/反量化、CPU 线程与内存带宽、GPU 队列、被淘汰专家的机会成本和调度开销。CPU/GPU 可以并发，完成时间不能简单按所有任务串行相加。H 也应考虑可被覆盖的部分，最终优化对象是关键路径时延。

### 3.3 复用距离和循环拓扑

| 结构 | 重复访问间隔 | 潜在效果与限制 |
|---|---|---|
| 逐层循环 | 同一层的重复调用相邻 | 专家较易保留，但普通 LRU/简单保留也可能已取得大部分收益 |
| 多层块循环 | 要经过块内其他层才再次使用 | 专家之间缓存竞争更大，阶段与复用距离可能更有用 |
| 整栈循环 | 要穿过整个循环栈 | 预取提前量可能更大，同时保留成本与被淘汰概率也更高 |

Loopie 使用逐层两次循环；LoopMoE 的主 3B 配置使用两层块重复四次。不能为了调度方便，把已训练的 block-loop 随意改为 layer-loop；这会改变模型函数。[Loopie](https://arxiv.org/html/2607.16051v3)、[LoopMoE](https://arxiv.org/html/2606.04438v2)

### 3.4 最容易失效的条件

- 模型本来就能全驻留 GPU，或实际专家 working set 能被简单缓存容纳。
- 相邻循环重合只是全局热门专家造成；LFU/分数缓存已经足够。
- 每个专家每次服务的 token 太少，传输无法被剩余循环摊销，CPU 执行反而更快。
- 大 batch/prefill 几乎激活整个专家池，集合重合很高，但没有足够缓存容量保留它。
- 只循环两次，阶段自适应和多轮预测没有足够使用窗口。
- 瓶颈是 attention、KV、kernel launch 或调度同步，减少专家传输并不能显著降低总时延。

## 4. 最小方法：先验证阶段感知保留

建议最初固定权重、原始 top-k、KV 语义和循环次数，只调整存放位置、传输时机和计算设备。不要同时引入专家剪枝、路由替换、跳循环、近似输出缓存或 speculative decoding，以免无法解释收益。

### 4.1 记录与预测信号

使用 t 表示生成 token 的步骤，r 表示 loop，l 表示物理层，e 表示专家。可比较三类历史：

1. 同 token、同物理层、上一 loop 的路由。
2. 上一个生成 token、同物理层、相同 loop 阶段的路由。
3. 请求内更长期的 gate 分数与激活频率。

最小模型可以是分阶段统计表或很小的线性预测器，不必一开始训练复杂网络。候选附加信号包括 top-k 边界 margin、路由熵、连续使用次数、剩余 loop 次数、距下一次使用的执行间隔。margin/熵是否预测路由稳定性需要实证，不能当成已校准的概率。

深度循环内部通常没有 dLLM 那种现成的词表输出 confidence。OLED 的直接迁移基线可把 confidence 置为常数，只保留 gate/频率、容量分配和复用感知补偿；替换为 margin 等信号的版本应另列为增强基线，不能称为原版 OLED。

### 4.2 最小策略

- 当前 GPU 命中的专家正常计算。
- miss 根据当前负载、硬件成本和预计再次使用价值，选择 CPU 或 GPU。
- 中间阶段优先保留实测稳定的专家；入口/出口采用各自的经验路由先验。
- 根据下一次使用距离和容量竞争决定保留期限；预取仅在有可用带宽及足够提前量时进行。
- 最后一轮降低“本 token 内继续复用”的价值，但保留下一 token 的复用项，不能机械清空缓存。

这个算法框架与 OLED/HybriMoE 具有继承关系。研究贡献应由消融证明：循环阶段/拓扑信息带来的增量，无法被不看 loop 的历史分数方法同样获得。

## 5. 按成本递增的初步实验

### 实验 A：真实生成的路由轨迹

建议先用公开 Foil 小模型。官方模型集合提供 Base、Foil-3、Foil-2、Foil-1，均为 553.7M 参数，分别为 8 层×2 次、4 层×4 次、2 层×8 次、1 层×16 次；每层专家数也随配置改变。它们适合观察拓扑与路由，但这些配置的差异不能被解释成只改变 loop 次数的因果消融。[模型卡](https://huggingface.co/ShourenWSR/how-to-loop-moe)

建议最小规模：先取两种配置，文本/问答、数学、代码三类各约 64 个 prompt，生成 128 token，batch=1。先固定模型支持的循环数；之后再加 batch=4/16、长上下文和 prefill 轨迹。不要在只训练两轮的 checkpoint 上直接任意增加循环数。

逐次记录：request ID、prefill/decode、token/位置、物理层、loop、专家 ID、gate 分数、每个专家 token 数、专家权重字节数与时间顺序。只读 hook 需单独计时，真实性能评估时关闭大规模轨迹导出。

对固定 top-k，定义同 token 相邻 loop 的复用覆盖率：

\[
O_{t,l,r}=\frac{|E_{t,l,r}\cap E_{t,l,r+1}|}{k}.
\]

同时报告 Jaccard，两者不能混用。独立均匀 top-k 选择时，O 的期望为 k/E；更强的空模型是保持每层/阶段专家边缘频率、打乱跨 loop 配对，排除热门专家造成的虚假时序信号。

至少输出：

- 分物理层、分 loop 转移的 overlap/Jaccard 热图与分布，不只报全局均值。
- 上一 loop 与上一 token 同阶段分别能预测多少下一次路由。
- 独特专家数、连续复用长度、复用距离/工作集字节数。
- 逐 token 指标与 batch 专家并集指标；两者回答不同问题。
- gate margin/熵与未来复用的关系，入口/中间/出口是否真的分离。

继续条件：跨 loop 信息比全局热度、上一 token 历史提供稳定的额外预测能力。否则先不要写复杂调度器。

### 实验 B：相同预算的轨迹回放

先比较缓存算法，不必实现完整推理系统。所有方法共用同一物理专家身份、访问顺序和缓存字节预算；不能让基线把循环权重复制多份。

| 级别 | 基线/方法 |
|---|---|
| 简单策略 | LRU、LFU、静态热门专家；保留上一轮专家 |
| 分数缓存 | HybriMoE 的历史分数策略 |
| 最近邻强基线 | OLED 式保留，confidence=常数，并保留其负载/复用思路 |
| 候选方案 | 上述策略只增加 loop 阶段/跨 token 同阶段历史，再逐个加剩余循环数、复用距离 |
| 离线上界 | 同约束的完美未来路由；等大小专家、固定串行访问、无预取时可用 Belady 作为最少 demand miss 参照 |

扫描约 5%、10%、20%、40%、80%、100% 专家权重缓存，并在“刚好能容纳循环活跃工作集”的位置加密采样。全模型显存还要扣除常驻权重、KV、激活、调度缓冲区和双缓冲，不能把专家缓存百分比误当作总显存百分比。

报告按需 miss 数、按字节计算的命中、每 token H2D 字节、重复加载和错预取字节。增加预取或 CPU 执行后，Belady 不再是端到端最优调度器；要用包含传输、队列与预算的事件模拟，并明确 oracle 知道未来、不能在线部署。

继续条件：强基线距离可实现 oracle 仍有明显空间，且 loop 信号能缩小差距。如果简单 LRU 或 OLED 已接近上界，应收缩方向或转向不同资源条件。

### 实验 C：微基准与端到端原型

先测真实平台：单专家 H2D、GPU 计算、CPU 计算、激活往返、不同每专家 token 数、CPU 线程数与同时传输时的带宽。CPU 应使用有竞争力的内核，不能用低效 Python 路径人为制造 GPU 调度收益。

然后在同一推理后端实现关键策略，以固定 checkpoint、精度、top-k、KV 策略和输出长度比较。HybriMoE/OLED 若移植核心策略，应清楚标为适配版；不要把不同框架/量化内核的差异归为算法收益。

Foil 很小，在常见 GPU 上需要人工限制专家缓存，因此它用于机制验证，不足以证明现实部署价值。后续可用公开 [Loopie-6B-A0.6B-preview](https://huggingface.co/zitian-gao/Loopie-6B-A0.6B-preview) / [Loopie-20B-A2B-preview](https://huggingface.co/zitian-gao/Loopie-20B-A2B-preview) 验证；两者使用逐层两次循环，不能替代多轮块循环的阶段实验。20B 模型在 BF16 下仅权重约需 40 GB，可选择确实无法全驻留的设备/精度组合；4-bit 情况必须重新核算。[论文与配置](https://arxiv.org/html/2607.16051v3)

精确的 Chen 等 LoopMoE checkpoint，本轮未核实到明确作者发布入口，不能把 Foil 仓库中也叫 `LoopMoE` 的类误认作它。若要复现原论文阶段热图，需要原模型权重或作者提供 trace。

端到端至少报告：

- prefill TTFT 与 decode ms/token，吞吐量和 p50/p95 时延。
- 每 token 权重 H2D 字节、GPU 等待权重时间、CPU 补偿暴露时间。
- 总峰值显存、专家缓存容量、CPU 线程/内存与实际有效传输带宽。
- 调度/预测/同步开销、预取覆盖率和错预取流量。
- 冷启动、固定 warmup 后结果分别报告；配对请求顺序，重复测量并给出波动。
- 固定输入轨迹下 logits 误差、路由一致性；自由生成的一致性/质量检查。不能只因为路由算法未修改，就声称浮点输出逐位相同。

### 实验 D：证明 loop 信息是必要的

最关键消融是“同一个调度器、同一套成本模型，有无 loop 特征”，随后去掉入口/出口区分、上一 token 同阶段历史、剩余循环次数、复用距离或 CPU 路径。

另做无泄漏对照：将 loop 阶段特征打乱，或把所有阶段统计合并，保持其他策略完全相同；评估集与统计拟合请求分离。若准确率和系统收益不下降，说明所谓 loop-aware 改动没有提供有效信息。

跨模型比较用于泛化。普通非循环 MoE 可作为附加负对照，但不能直接以不同模型的绝对 ms/token 证明调度创新。

## 6. 决策标准与推荐顺序

最先做两件事：**真实生成路由 profile；同预算 LRU/分数缓存/OLED 式保留/oracle 回放。** 它们能以较低成本判断是否值得做完整 CPU–GPU 调度。

建议事先设定自己的工程门槛，例如相对最强适配基线能否稳定减少约 10%–15% 的 decode 时延，并在多个显存预算及另一模型上成立。这是投入决策门槛，不是投稿标准，也不是对实际收益的预测。

若端到端中专家传输/补偿只占 10%，即便完全消除，按简化 Amdahl 分析也最多约 1/0.9=1.11 倍加速。应先确认瓶颈，再增加算法复杂度。

可用于开题表述的问题是：**在精确路由与有限 GPU 显存下，如何利用循环阶段和物理专家复用距离，联合决定专家驻留、提前加载和 CPU/GPU 执行，并优于已有跨迭代缓存方法的直接迁移？**

这一定义承认已有工作，也给出了可以被实验否定的增量假设。
