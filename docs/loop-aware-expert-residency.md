# Looped MoE 专家调度方法设计：根据下一次物理层访问决定驻留

> 2026-11-21 更新。扩大样本后，Loopie-6B 的 5% 预算复现了局部收益，精细阶段和双历史仍缺少独立收益证据。质量复核又发现当前 Looped-MoE 检查点异常，Foil 的自由生成大量重复。下文保留方法设计与 11 月 18 日开发回放时的判断。当前实验排序见[研究笔记](research-note.md)，数值和质量限制见[扩样结果与生成质量复核](expanded-results-2026-11-20.md)。

**我建议把 loop 用在两个具体判断上：下一次访问这个专家池时，哪些专家可能被选中？为了等到这次访问，值得让它们占用多久的显存？** 前一个问题利用同一 token 沿深度演化的路由，以及上一 token 在相同深度的路由。后一个问题利用模型已知的执行顺序。同样是“上一轮命中过的专家”，在逐层循环中可能马上要用，在整块循环中却要与另外七层争用缓存。这个区别能改变实际淘汰谁，也能用现有轨迹检验。

### 两条历史是否提供了重复的信息？

我按现有划分，只在每个模型的 **6 条拟合请求**上重新汇总。对于既有上一轮、又有上一 decode 位置的目标访问，记 A 为当前 token 上一轮的 top-k，B 为上一 token 同阶段的 top-k。把目标实际选中的每个专家按它在 A、B 中是否出现分到四列，分母是这些目标访问的实际专家选择总数。这个口径排除了每个 token 的首轮和每条请求的首个 decode 位置。[轨迹字段](../README.md) · [拟合与评估划分](../loop_moe/replay.py)

| 模型 | 只在 A | 只在 B | 两者都有 | 两者都没有 |
| --- | ---: | ---: | ---: | ---: |
| Foil-1 | 25.09% | 12.46% | 8.17% | 54.28% |
| Foil-3 | 36.34% | 12.46% | 20.74% | 30.46% |
| Loopie-6B | 26.16% | 8.44% | 4.73% | 60.67% |
| Looped-MoE | 18.70% | 33.21% | 38.24% | 9.85% |

在 Looped-MoE 的第二轮，如果只从本 token 的第一轮找候选，会漏掉 33.21% **上一 token 的第二轮已经提示过**的目标选择。这给保留“刚才没选中、但在这个阶段常回来”的驻留专家提供了直接动机。Loopie 的情况不同，两个来源合起来也漏掉 60.67%，预测器需要给其余专家保留由 gate 历史或长期热度决定的优先级。以上比例衡量候选覆盖；实际命中还取决于专家是否已经在缓存中、为保留它需要牺牲谁。

## 2. 与 OLED-MoE 的区别在哪里

OLED-MoE 已经把 dLLM 相邻去噪迭代的复用变成了驻留和补偿策略。它用 token confidence 加权 gate 分数，汇总得到专家优先级，把本轮未激活的驻留专家优先级置零，按层的激活与缓存利用情况分配容量，并在 miss 时结合当前负载与未来复用安排 CPU 执行或 H2D 加载。简单把去噪轮次换成深度轮次，或者给上一轮专家统一加分，与这项工作过于接近。另一个值得注意的细节是，在当前 batch=1、单位置的回放中，同一 token 的标量 confidence 在 OLED 的归一化公式中会约掉。[OLED-MoE §4.3–4.4](https://arxiv.org/html/2609.33385v1)

我们可以检验一个更窄的主张：**当多个物理专家池争用同一块 GPU 缓存时，目标深度阶段能帮助识别哪些专家会回来，已知的层访问顺序能帮助决定哪些值得等。** 例如，在 Looped-MoE 第一轮第 0 层算完后，一个尚在缓存、这次没有被选中、上一 token 第二轮第 0 层却用过的专家，可以获得正的保留价值。但如果七个中间层有更紧迫的需求，它仍可被淘汰。对 Loopie 第一轮则相反，同层第二轮就在眼前，普通 LRU 往往已经作出了合适选择。两种情况下都允许已有策略赢，这是检验 loop 信息是否值得使用的必要对照。

## 3. 第一版方法：把缓存条目估值到下一次同池访问

先做 batch=1 的按需加载与驻留，保持原模型的路由与执行顺序。缓存键为 **（物理专家池，专家 ID）**，多轮共享同一份权重。每个驻留条目只预测到该池的下一次访问，访问结束后重新估值。这样只需要一个小统计表和模型原有的执行顺序。

**把预测目标和信息到达的时间分开。** 取下一 token 第 $r$ 轮的实际专家集合 $E_{t+1,p,r}$ 为例。在 token $t$ 的第 $r$ 轮结束后，就能记下 $E_{t,p,r}$，作为跨 token 的同阶段参考。等到 token $t+1$ 的第 $r-1$ 轮结束，又能用刚观测的 $E_{t+1,p,r-1}$ 更新对同一目标的估计。只有后一个时点能使用这条同 token 历史。第一版按下一次同池访问做驻留，在中间各轮先服务更近的需求；保存跨 token 的路由 ID 或分数只需元数据，不要求从 $t$ 到 $t+1$ 始终保留相应权重。对于 $r=0$，同 token 上一轮标为缺失，上一 token 末轮可作为单独的边界特征。

| 执行结构 | 同一 token 内同池相邻两轮之间的其他专家池访问数 | 调度含义 |
| --- | ---: | --- |
| Loopie；Foil-1 的循环部分 | 0 | 刚用过的权重常已在缓存中，要与 LRU 比较新增命中 |
| Foil-3 的四层循环块 | 3 | 同池的目标仍是下一轮，等待期间另外三层可竞争缓存 |
| Looped-MoE 的八层循环块 | 7 | 仍能保留上一轮的路由记录，是否保留权重取决于跨越七次访问的机会成本 |

三种模型家族共享的是按物理池和阶段索引历史、按真实访问顺序决策的规则。阶段概率可以按 checkpoint 拟合；跨架构共享一组系数的效果需要另行验证。Foil 的非循环 head/tail 只有跨 token 历史。[各模型的物理池访问顺序](../loop_moe/adapters.py)

1. **确定下一次访问。** 当前为 token $t$、物理层 $l$、阶段 $r$。若该池在本 token 还有下一轮，目标是 $(t,l,r+1)$；若已到最后一轮，目标是 $(t+1,l,0)$，以请求继续生成为条件。Foil 的 head/tail 也计入访问间隔，并按各自实际的下一次访问估值。
2. **估计目标阶段选中专家的概率。** 对已访问池的候选专家，记录两个布尔量：它是否出现在刚结束的访问中，它是否出现在目标阶段最近一次已完成的同阶段访问中。预测下一 token 首轮时，第二项取当前 token 的首轮。用拟合请求统计每个“物理层、源→目标阶段、两个布尔量、最近 gate 排名档”组合的选中率，分母包括该组合下所有候选专家的机会次数，分子是目标实际选中的次数。排名取现有 top-2k 记录，榜外单列。样本稀少时按计数向跨阶段的同类统计收缩，缺少历史时使用已观测到的 gate 历史/热度。所有策略共用同一候选集合；未驻留的专家只能在真实路由要求时加载。
3. **把概率换成缓存优先级。** 从当前决策点到池 $l$ 的下一次访问，令 $d_l$ 为中间尚需经过的其他池访问次数。$d_l$ 由模型执行表直接得到，每经过一次访问就相应缩短。一个可直接回放的起点是

$$
V_{l,e}=\frac{\hat p_{l,e}\, H_{l,e}}{b_{l,e}(1+d_l)} .
$$

这里 $H$ 是一次 miss 的权重传输代价，$b$ 是专家权重字节数。首轮回放优化 H2D 字节，可直接令 $H=b$；于是优先级就是“下一次被选中的概率 / 还需占用的访问步数”。它是一个可被消融的贪心近似。两次访问之间遇到的真实 miss 数只有事后才知道，不能用轨迹中的真实复用距离给在线方法打分。若等步数折扣过强，先与完全去掉该项比较；有了机器测量，再检验以预计占用时间和暴露传输时间替换步数及字节是否值得。

4. **按需执行、软保留。** 对当前 top-k 正常服务。一次访问内采用与基线相同的服务顺序，算过的专家可立即放弃长期驻留。容量冲突时，从可淘汰的驻留条目和刚服务完的条目中移出最低价值者，平分时按 LRU。其他池的路由概率沿用最近一次估计，时间距离按当前位置更新。下一层出现高价值需求时可立即收回空间，无需为本轮专家预留固定配额。真实实现中应把正在计算或搬运的权重缓冲计入相同的峰值显存限额。

这一版特意把问题限制在“留谁”。若按需回放已有稳定增益，同一个 $\hat p$ 可以接入 OLED 式 miss 补偿，比较把专家搬上 GPU 与本次交给 CPU 的完成时间。届时需用实机测量 CPU 计算、激活往返、H2D 以及它们可重叠的部分，重新估算留住专家实际节省的等待时间。

## 4. 最先做的对照与决策标准

| 用现有 trace 做什么 | 公平对照 | 结果如何影响决策 |
| --- | --- | --- |
| 检验两条路由历史的独立贡献 | 固定候选、拟合请求和模型容量，对比 gate/EMA、加 A、加 B、加 A+B，再比较按阶段分表与合并阶段。另用同池最近若干次访问的通用滞后特征，给它与 loop 方法相同的历史跨度 | 看留出请求上的目标 top-k 召回，同时在当时确实驻留的候选中比较固定保留数的召回。若普通滞后历史已经等效，结论应收缩为周期性访问历史有效 |
| 分清预测收益与拓扑收益 | 四格回放交叉比较“通用历史 / 分阶段双历史”与“不折扣 / 按距离折扣”。两种预测器都能使用同一执行表做距离对照。另保留 LRU、LFU、静态热门、Score EMA、固定奖励和 gate-only | 每个预算报告每个生成位置的 H2D 字节、字节命中率、相对最强在线基线的变化。单列因保留额外命中的字节和因挤出其他专家损失的字节，判断净收益来自哪里 |
| 排除弱基线与数据泄漏 | 加入 OLED 保留适配版，包含 gate 优先级与按层自适应容量；现有 oled_gate_only 只覆盖其中一部分。若以后启用 CPU 补偿，双方使用同一执行器。另打乱拟合数据中同层同阶段的前后配对，保留阶段热度和真实评估顺序 | 若动态分层配额或阶段热度已解释全部改进，应报告这一结果。Belady 只作同一访问顺序、相同准入规则下的离线参考 |

优先看 **Looped-MoE 的 10% 和 20%**，它同时具备跨 token 同阶段信号和明显的层间竞争。同步看 **Loopie 的 5% 和 10%**，把首轮→次轮和末轮→下一 token 首轮分开统计，检验增益出在哪个边界。用 **Foil-1 / Foil-3** 检查具体轮次是否比“首轮/末轮”两类标签多提供信息。主表仍保留已有六档预算，按请求给出配对差值及波动。既有 12 条评估请求的汇总结果已用于选方向，适合作为开发对照；最终结论需要一批此前未查看的新请求，按请求隔离拟合、选参和测试。

**我的取舍是先验证净减少的搬运量，再决定是否投入推理后端。** 如果分阶段历史在多个紧张预算上优于同跨度的通用历史，且扣掉缓存挤出损失后仍有收益，就值得在真实显存受限的设备上做端到端测试，报告 decode ms/token、GPU 等权重的时间、峰值显存和调度开销。如果只有距离折扣有用，就把贡献收窄为利用已知执行顺序的缓存替换。如果提升主要来自胜过 0% 命中的 LRU，而追不上 EMA 或 OLED 保留适配版，我会停止扩展这个方法。现有采集关闭 KV cache、逐步重算前缀，回放只取新增位置并将专家请求串行化；这些命中率和推算字节数都不能直接换算为实际加速。[采集与回放口径](../README.md)

5% 下 12 条请求有 11 条受益，10% 下只有 5 条受益。分解定位了收益和损失发生的访问，尚不能认定是哪个先前的淘汰决定造成的。有意思的是，5% 下在同一组 Score EMA 驻留候选中固定取两个，双历史预测第二轮的召回仍高于通用历史（9.33% 对 8.79%，分母为所有目标专家），实际回放却在第二轮多加载 1,619 次。需要沿着跨池竞争与淘汰顺序追溯这笔损失。Loopie 的两轮结构中，完整阶段对与“是否跨 token”的边界标签一一对应；这个模型单独无法证明使用精细轮号的价值。预测诊断（`runs/residency-20261118-v1/Loopie-6B/prediction_requests.csv`）

**Foil 和 Looped-MoE 限定了方法的适用范围。** Foil-1 在 10% 下给双历史加距离后命中率从 49.46% 升至 64.78%，但通用历史加相同距离达到 66.39%，双历史在 12 条请求上全部多搬权重。Foil-3 的 10% 两者仅差 0.10 个百分点，改善和退化各 6 条。Looped-MoE 的全池 top-k 召回中，带 gate/EMA 的跨 token 同阶段预测达 67.72%，加入上一轮并分阶段为 67.46%；限制到 20% 预算下同一组驻留候选后，双历史和通用历史的召回分别为 58.42% 和 58.46%。路由重合度可以很高，而两种可部署方法对保留谁的判断仍十分接近。Foil-1 回放（`runs/residency-20261118-v1/Foil-1/residency_summary.csv`） · Foil-3 回放（`runs/residency-20261118-v1/Foil-3/residency_summary.csv`） · [预测与请求对照](residency-pilot-2026-11-18.md)

**下一步只做一个优先实验：在相同距离和执行规则下，检验目标为下一 token 首轮时使用同阶段历史，能否在保住第二轮命中的同时减少总搬运。**

1. 先在已有 Loopie 5%/10% 轨迹回放中记录两策略淘汰对象不同的事件，标出双方淘汰的专家下一次实际使用的池、阶段和距离，以及是否在当前已知 top-k 内尚待服务。未来信息仅用于事后归因。所有策略均在 gate 已知后按专家 ID 顺序服务，后一项可以识别服务顺序造成的重复加载。若该项占比大，双方都采用先服务已驻留专家的次序复核，并重新计算同口径的基线和 oracle。[执行与淘汰实现](../loop_moe/residency.py)
2. 对照固定为通用历史加距离。另跑“只用跨 token 同阶段历史加距离”“合并阶段的双历史加距离”和一个混合版本：预测跨 token 首轮时使用同阶段历史，预测同 token 内后继时使用通用历史。所有版本共享 gate/EMA、缓存准入和预算。报告首轮、后续轮及总 H2D，按请求配对。混合版本的缓存状态会互相影响，其收益要实际回放，不能直接把当前两条曲线的最佳部分相加。
3. 预先固定规则后，用未看过的请求验证，在 Foil-1/3 和 Looped-MoE 上按相同规则复核。若收益只在 Loopie 的单档预算出现，保留为特定工况的发现；若跨预算能重复减少总 H2D，再测真实设备上的传输等待、调度开销和 decode 时延。现有 OLED 适配只覆盖驻留和层配额，端到端比较还需统一 CPU 补偿路径。
